# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

llamatron is a text UI that helps people compose electronic music in MIDI, for Ableton Live and, later, other DAWs. Its features are inspired by Ableton's Session View, hardware sequencers like the Elektron Monomachine and the Sequentix Cirklon, and software trackers. The Python classes underneath are internal: no person is expected to use them as an API, so they can change freely to suit the tracker. It's at an early stage. The third-party dependencies are `mido`, `PyYAML` and `textual`, pinned in `requirements.txt`, which `setup.py` also reads. The package is `llamatron`, in `src/llamatron`, and the code and its tests import it by that name, so it has to be installed (as below) before anything runs.

## Commands

Set up the virtual environment once. This also installs the `llamatron` command, which `setup.py` points at `llamatron.cli:main`, and `-e` makes it use the code here rather than a copy:

```
python3 -m venv .venv
.venv/bin/python -m pip install -e .
```

Tests use the standard library's `unittest`. Run them from the repository root, after the install above:

```
./run_tests.sh                # all tests, in parallel: about 20 seconds
./run_tests.sh test_name      # tests matching a name
./run_tests.sh --serial       # all tests in one process, the plain unittest way: about two minutes
```

Always run the full suite with `./run_tests.sh`, which runs `test/parallel.py`: one process per test class, as many at once as there are cores, reporting every failure in full and the total count. It exits with a failure if any class fails, so check its exit code or its last line (`OK` or `FAILED: ...`) before committing. `.venv/bin/python -m unittest discover -s test` still works and gives the same results, just slower.

Don't add `__init__.py` to `test/`, because a package with that name would clash with Python's standard library `test` package.

`tools/` keeps scripts for working on llamatron that are worth running again, rather than one-off scripts, and the user wants reusable scripts preserved there instead of being lost in a temporary folder. They follow the same style rules as the program and start with the GPL header below their `#!` line, and each one's docstring says what it's for and how to run it. Run them from the top folder:

```
.venv/bin/python tools/compare_renders.py capture /some/folder   # before a change that shouldn't alter the music
.venv/bin/python tools/compare_renders.py compare /some/folder   # after it: lists every file that differs
.venv/bin/python tools/check_unused_imports.py                   # unused imports in src/, test/ and tools/
.venv/bin/python tools/show_midi.py some.mid                     # a MIDI file's notes as names and lengths
```

Before committing a change to code, run `tools/check_unused_imports.py`. Before and after a refactoring, or any change that should leave the music alone, use `tools/compare_renders.py`, which proves byte for byte that every example still renders the same, or shows which songs changed.

## Version

`src/llamatron/version.py` holds `VERSION`, a string of three whole numbers separated by dots, like `1.0.2`, which `setup.py` reads, the tracker's title shows, and every saved song file records as `version`. Versions are compared number by number with `version_numbers()`, never as decimals. Bump the last number in every commit that changes Python code under `src/`, and leave the first two to the user. Commits that only change docs, notes, tests or examples don't bump it. The program and the files share the one number.

## Code

Source code is in `src/llamatron`, and tests are in a `test` folder at the top.

`Note` (`src/llamatron/note.py`) is immutable and built from a name, an octave and a required length. Lengths are fractions of a whole note, so `0.25` is a quarter note and `0.5` is a half note. `Rest(length)` is the same but silent. Notes compare and hash by MIDI number and length rather than spelling, so `Note('C#', 4, 0.25) == Note('Db', 4, 0.25)` and `Note('B#', 3, 0.25) == Note('C', 4, 0.25)`, while `name` keeps the spelling it was given.

llamatron's own octave numbers start at `C0`, which is MIDI note 0, so the highest note is `G10` (127). Every DAW labels octaves differently, and Live, the only DAW implemented so far, labels MIDI note 0 as `C-2` (see `LIVE_OCTAVE_OFFSET` below). The user has decided that the song file will store llamatron's own numbering, starting at 0, and that the tracker will show octaves through a display setting on the song, defaulting to Live's labels. That isn't built yet: today the file and the tracker both use Live's numbers, and `LATER_IDEAS.md` describes the change. Notes outside the MIDI range can't be constructed, and that includes `Cb0` and `G#10` and above. Double sharps and double flats aren't supported.

The octave is stored as `octave_number`. `half_step(n)` returns a new note of the same length, spelled with flats if the note's name has a flat and with sharps otherwise.

`Chord` (`src/llamatron/chord.py`) is an immutable group of notes, and chords compare by their sorted MIDI numbers and lengths. A chord's `length` is its longest note's, and that's how long it occupies in a clip. `ChordType` values are half steps above the root. `Note.to_chord(typ)` builds a chord upward from the note using `half_step`, so every note gets the root's length and chord tones follow its sharp or flat rule rather than proper chord spelling: C minor contains `D#`, not `Eb`. `src/llamatron/chord.py` imports `Note`, so `to_chord` imports from `llamatron.chord` inside the method to avoid a circular import.

`Scale` (`src/llamatron/scale.py`) is an immutable root note and `ScaleType`, and `Degree.to_note` reads notes from it. `ScaleType` values are one octave of half steps including the root (`0`). Scale types with identical values are Python enum aliases, so `ScaleType.AEOLIAN is ScaleType.MINOR` and `list(ScaleType)` includes only the first name.

`ClipGrid` (`src/llamatron/clip_grid.py`, which was `Song` in `song.py` before the refactoring) stores the finished clips a song renders into, a grid of `Clip` objects, one cell per `(Scene, Track)`, in a dict nested as `{scene id: {track id: clip}}`. The ids exist because names don't have to be unique, and other types don't need them. Tracks and scenes get theirs from `add_track` and `add_scene`: each song counts tracks and scenes separately from 0 in the order they're added, and the id is `None` before that. This means a track or scene can only join one song. Clips get a unique id when created. `Track`, `Scene` and `Clip` compare by identity, and grid methods reject scenes and tracks that aren't in the song.

`tempo_at(scene)` resolves as scene, then song, and `scale_at(scene, track)` resolves as clip, then scene, then song, both reading the current values each time. Clips deliberately have no tempo, because Live has no per-clip tempo for MIDI clips. Only `ClipGrid` has a default tempo (120, minimum 10), and a scene tempo of `None` means it uses the song's. A song's `scale` can be `None`, so `scale_at` can return `None`. Scales will be used by generator objects that haven't been designed yet.

`Clip.notes` is a list where each position is a `Note`, `Chord`, `Rest` or `Degree`, played in order. The setter also accepts shorthand and converts it to objects: `'E4'` is a `Note`, `3` is a `Degree`, and each dash is a quarter note of rest, whatever the `note_length`.

Binding is as late as possible, and the user wants new features to keep it that way. A `Degree` (`src/llamatron/note.py`, numbered from 1) stays a degree until `ClipTree` converts it with `song.scale_at(scene, track)`, so a clip follows its scene's or song's scale. A `Note` or `Degree` with a length of `None` takes `Clip.note_length`, which `clip.resolved_notes()` fills in without changing the clip. Missing scales and lengths raise `ValueError` at render, before any file is written. Generators keep degrees as degrees. Chords hold only `Note`s so far. `Clip.trim(n)` keeps the first `n` positions in place and returns the clip. `Clip.length` uses the same whole-note units, and `None` ends the clip after its last position, while any other value adds silence or cuts notes off to fit. There's no time signature yet, but time signatures are planned (see `LATER_IDEAS.md`), so don't design anything that rules them out. Tempo is in quarter notes per minute.

Fields on `ClipGrid`, `Track`, `Scene` and `Clip` are editable unless the user says otherwise. Today the `_Validated` descriptor checks every assignment, but that's being replaced: the user always wants explicit accessor methods, so that the code is clear and obvious. A class changes another's data only through a method like `set_name(name)`, which validates what it's given, and reads it only through one like `get_name()`, never through descriptors, properties or other accessor magic. Accessors aren't added automatically for every field: a class has only the ones other classes actually use, so its accessors show what's part of its contract with other classes. Object orientation is a design goal throughout, and `LATER_IDEAS.md` plans for every object to save and load itself with `to_data()` and `from_data()`, with the song calling them on everything it holds, which replaced `song_file.py`. Two more readability rules from the user, for all code: every string used as a value or a name in code, like a file key (`'root'`, `'pattern'`), a setting, a kind (`'arp'`) or a mode (`'forward'`), is a named constant, never written out where it's used, so that typos can't happen and its meaning is clear. A constant used by only one file is defined at the top of that file, and one shared between files goes in a module of the package, like `composition/defaults.py` for defaults and `composition/file_format.py` for the format's names and lists. Symbols the format defines count too: note names are `NoteName` constants in `note.py`, like `NoteName.C_SHARP` for `'C#'`, with the lists built from them (`NOTE_NAMES`, `SHARP_NAMES`, `FLAT_NAMES` and `ROOT_NAMES`, which the tracker's root pickers use), and chord symbols are `ChordSymbol` constants, like `ChordSymbol.DOMINANT7` for `'dom7'`, and the tables that use them refer to the constants. The same goes for numbers with a meaning, like the limits of a range: `MIN_PROBABILITY` and `MAX_PROBABILITY` rather than 0 and 100, with shared limits in `composition/limits.py`, and error messages built from those constants. Text only for people, like docstrings and comments, stays where it is, but every message the program shows or raises is a constant at the top of its file, named like `MSG_UNKNOWN_SCALE_TYPE`, written as a template and filled in with `.format()` where it's used, so that wording can be edited in one place and kept consistent. Literal braces in a template are doubled, like `{{ root: F }}`. Each constant is defined on its own line, never several at once with tuple syntax like `LOW, HIGH = 0, 100`, which the user finds hard to read. Tests are held to all of these rules too, as the user requires: limits come from the program's constants (`MAX_REGISTER_VALUE + 1`, not `128`), a number that means something gets a name, messages and format strings are constants, and tests of the demos read what they check from the demo's YAML, so that hand edits don't break them. When a test checks text the program shows, like a row label, a key's name or a message, it imports the program's constant for that text (like `ROW_LABELS[Row.DEGREE]` or `MSG_NO_SUCH_SCALE`) rather than writing the words out again, so that renaming something in the program doesn't break its tests. Most existing tests don't do this yet, and `LATER_IDEAS.md` plans the refactoring. And a line whose purpose isn't obvious, like a regular expression or a long expression, is given a function or method whose name says what it means, such as `is_root_note(text)`. That includes list and dictionary comprehensions: anything more than a plain copy or filter goes in a function or method whose name says its purpose, even if it's one line. Every class declares its data members with `__slots__`, so none can be added by mistake, and each class in a hierarchy declares its own, even `()`. Dataclasses use `@dataclass(slots=True)`. The exceptions are classes that only hold constants, and subclasses of classes from outside llamatron, like Textual's screens, enums and exceptions. `test/test_slots.py` checks this, with a `NOT_YET_CONVERTED` list of modules still to do that shrinks as each is converted. New code follows these rules now. The existing code doesn't yet, and `LATER_IDEAS.md` plans an audit. The exception is `id`, which is read-only. `Note`, `Chord` and `Scale` remain immutable.

Renderers live in `src/llamatron/renderers`, and their tests go directly in `test/`, because discovery doesn't reach subfolders of `test/` without `__init__.py` files. `ClipTree` (`src/llamatron/renderers/clip_tree.py`) takes a directory and a `ClipGrid`, and `render()` writes `<scene_id>-<track_id>-<clip_name>.mid` for each filled slot (just `<scene_id>-<track_id>.mid` if the clip has no name, with ids zero-padded to three digits, and with whitespace and slashes in the name replaced by underscores), where a clip is named after the pattern it plays (the scene keeps the scene's name), with the file name (minus `.mid`) as the MIDI track name, a tempo, and the clip's notes at each note's velocity. It must never delete existing files in the directory. Other files get a printed warning, while a file with a name it needs to write makes it print a warning and stop without writing anything.

`AbletonProject(directory, song, template)` (`src/llamatron/renderers/ableton_project.py`) takes the same inputs and writes a Live 12 set to `<directory>/<directory name>.als`, with clips in Session View and the scenes laid end to end in Arrangement View. A `.als` file is gzipped XML with no public documentation, so it edits a template Live saved, `src/llamatron/templates/live12.als`, installed with the package, whose first MIDI track must keep a clip because all the clip details are copied from it. Ids on tags ending in `Target`, `Targets.N` or `Pointee` must be unique across the set and below `NextPointeeId`. Tempo must be set on both the control and its automation. To check the format, read Live's own sets in `Contents/App-Resources/Core Library/Templates` and its schema in `Contents/App-Resources/Schema`. Tests can check structure, but only opening a set in Live proves it loads. Neither renderer uses temporary files: `AbletonProject` builds the whole set as XML in memory, writing notes and envelopes straight into the template's clips, and writes only the `.als` once it's complete, while `ClipTree` writes its `.mid` files straight to the output folder. Any future temporary files must use `tempfile`, be documented, and be removed when they're finished with. Both renderers get note timing from `src/llamatron/renderers/timing.py`. A `Clip`'s `controls` are `Control(time, number, value, slide)` CC values, which sections, repeats and generators carry along. `ClipTree` writes them as control changes, with a slide sent as a value every `SLIDE_STEP`. `AbletonProject` writes one `ClipEnvelope` per CC number, pointing at the track's `MidiControllers/ControllerTargets.N`, where N is the CC number plus 2, after pitch bend and channel pressure. This was worked out from one set the user saved with a mod wheel (CC 1) envelope. Live draws a straight line between points, so a slide is just two points, and a value that holds gets a second point at the old value at the moment of the next one. Hold points and other CC numbers are unverified in Live. `test/test_matrix.py` is an end-to-end example of the classes underneath the tracker.

Generators live in `src/llamatron/generators`, with the same test layout as renderers: `arp` and `auto_ratchet`, the two that a chain can use, `blend`, which morphing uses, and `base`. A generator's list of values must only step through notes and chords, so rests never use up a value (`test/test_generator_list_steps.py` checks this, so add new list generators there). Each subclasses `ClipGenerator` (`base.py`) and implements `_generate(clip)`, returning new notes and a length. `generate(clip)` then returns a new `Clip` with the same name and scale, leaving the original unchanged, so generators can be chained. `Arp(step, order, seed)` plays each chord one note at a time for the chord's full length, and leaves notes and rests alone. It restarts from the beginning until it fills a set `length`, and a `ChordOrder` of `UP` or `DOWN` goes by pitch rather than the order the chord was built in. `Arp` also takes the Monomachine's settings. `octave_range` (1 to 4) plays the chord again in higher octaves, and `octave_jump` is `after_chord` or `after_each_note`: descriptive names rather than numbers, as the user asked. `offsets` is a step track of 1 to 16 values, each moving its note along the clip's scale (or by half steps with no scale). A `None` step is silent and doesn't use up a chord note, and the offsets restart with each chord. With offsets or a range, a single note is arpeggiated as a chord of one note. `AutoRatchet(counts)`, a current generator that the user plans to retire, chops each note or chord into that many adjacent equal repeats, using the next count in a cycle, and rests don't use one up.



`Clip.section(start, end)` and `Clip.repeated(times)` cut and repeat clips by time. `Blend(target, amount, mode)` moves a clip towards an equally long target, with `BlendMode.LEFT`, `RIGHT` and `MIDDLE` sweeping the target in from one side or the center.


`src/llamatron/composition/` holds the composition model, the objects a song file stores, each a `LlamaData` subclass with `to_data()` and `from_data(data, where, song)`, which checks the data with the same messages as before and keeps settings the file leaves out as `None`, meaning their defaults: `Song`, `Scene`, `Cell` (what one track plays in one scene), `Track`, `Pattern`, `NamedScale`, `Chain`, `ArpSettings` and `AutoRatchetSettings`, which are only checked when a chain uses them, so errors name the chain. Objects refer to each other by name, and the song looks names up. `test/test_composition.py` tests each class, and `test/test_llama_data.py` checks every subclass defines both methods. `Song.read_file(path)` reads a song file with `yaml.safe_load`, and `SongRenderer(song).render()` (`src/llamatron/playback/`) plays it into a `ClipGrid`, with a `CellPlayer` for each cell and a `PatternPlayer` for each pass through a pattern. Tests use the helpers in `test/rendering.py`. `src/llamatron/cli.py` is its command line, installed as `llamatron`. Without `--to` it opens the tracker, on a song if one is named, and with `--to` it renders instead. `--out`, `--template` and `--replace` are refused without `--to`. There's deliberately no separate command for the tracker, and `python -m llamatron` is the same as the command. `src/llamatron/song_writer.py` writes the same format. The format is mainly for machines now, but it stays readable for version control diffs where it can. `GENERATOR_SETTINGS` in `src/llamatron/composition/generator_settings.py` lists each generator's settings class, so new generators need adding there and using in an `examples/` song, which a test enforces. The format's rules are deliberate:

- A pattern holds `steps` and one list per row, mirroring the pattern editor: `degree`, `gate`, `dot`, `accidental`, `octave`, `chord`, `velocity`, `probability`, `glide`, `ratchet`, `ratchet_offset`, `grab`, `cc1` to `cc4`, `slide`, and for the registers `ax_note` to `dx_note`, `ax_velocity` to `dx_velocity` and `ax_add` to `dx_add`. The on or off rows, `glide`, `tie`, `grab`, `slide` and the registers' note and velocity rows (`TOGGLE_ROWS`), always hold `true` or `false` and never null, as the user asked, and the text UI shows them as `*` or a blank. Rows of all blanks are left out. Nothing is packed into one value, so there's nothing to parse apart, except that lengths stay as whole numbers or fractions like `5/16`, because decimals can't hold 1/3. Decimals are refused for step sizes and gates.
- Every step of a pattern lasts its `step_size`, which the pattern can set and otherwise comes from the song's `step_size` (default 1/16), so a pass lasts steps times step size. A step with a note sounds for its `gate`, a whole number or fraction of whole notes up to `MAX_GATE` (4), or one step if blank, made dotted (`d`, half as long again) or a triplet (`t`, two thirds) by its `dot` row. A gate can run past later steps but is cut at the end of the pattern, though glide still runs slightly into the next pass. A `tie` on an empty step (a step with a note can't have one, which the file refuses) keeps the note that played just before it, in play order, sounding to the end of the tied step, and the longer of the gate and the ties wins, so a note and three ties of 1/16 is a quarter note. A tie after an empty step or a dropped note is silence. Ties at the start of a pass are the one thing gates can't do: `PatternPlayer.play_pass` returns a `Pass` with `tied_from_before`, and `CellPlayer` lengthens the note the passes so far ended with (`_tied_on`, making it a `Held`), so a tie carries across repeats and loops of a clip but not into a new scene's clip, where it's silence, because clips are separate in Live. A morph's target's ties work inside the target, and ties at the start of a pass follow the cell's own pattern. A blank degree is an empty step, which is a rest, and a pattern needs at least one step. In a finished clip, a note whose gate reaches exactly to the next note is an ordinary position, a shorter one is followed by one rest per step, and a longer one is a `Held` (`src/llamatron/held.py`), whose sound lasts its own length while the next position starts after its place. Time signatures are still to come (see `LATER_IDEAS.md`). `drum: true` puts note letters in `degree`, and has no chords.
- Octaves are absolute, with no track offset, and are numbered as Live displays them for now, so `3` with degree 1 of C major is MIDI 60. llamatron's own numbering is two octaves higher, and `LIVE_OCTAVE_OFFSET` converts. That offset is specific to Live, the only DAW implemented so far. The file is to switch to llamatron's own numbering, with Live's labels becoming the tracker's default display (see the octave numbers bullet above, and `LATER_IDEAS.md`). A degree past the top of the scale wraps up an octave, for a scene with a smaller scale.
- Chord symbols come in two kinds, listed in `FIXED_CHORDS` and `SCALE_CHORDS` in `src/llamatron/composition/file_format.py`, in the order the editor offers them. Named symbols like `M`, `dom7`, `m7b5` and `M13` are exact half steps from the note, so they can leave the scale. Plain numbers `5`, `3`, `7`, `9`, `11` and `13` stack every other scale note, so they follow scale changes. A bare number always means a scale chord, which is why dominants are `dom7` and so on, as the user chose. Every symbol fits the editor's 5-character cell.
- Probability is rolled at render from the song's `seed`, once per repeat and ratchet slice, so that a render plays the same every time. It deliberately doesn't use Live's per-note probability. `ratchet` splits a step into equal notes in the same time. `glide` runs a note slightly into the next one, which a synth with glide turned on slides across, and it does nothing before a rest or the same pitch.
- A scene launches clips and has no length of its own: it lasts as long as its longest clip that doesn't loop. A clip plays its pattern `repeat` times and stops. `loop: true` repeats it until that longest clip ends, and every clip in a scene looping is an error at build. A clip with a repeat above 1 can `morph_to` a second pattern in a `morph_style` across its repeats, and the second pattern is looped or cut to match the first. There's no way to morph across a scene's repeats.
- A morph's target plays as it's written, without grabbing.
- `ratchet_offset` moves each ratchet slice further along the scale, or by half steps in a drum pattern. The song has four registers, `AX`, `BX`, `CX` and `DX` (`RegisterName`), the user's replacement for the Cirklon-style accumulators, which are gone. Their names are fixed, and `registers:` holds the settings that differ from the defaults, like `AX: { maximum: 3, wrap: true }`, with `default`, `minimum` and `maximum` from -127 to 127 (defaults 0, 0 and 10, in order minimum <= default <= maximum) and `wrap` (default false). A step's `ax_add` adds to AX as it plays, even with no note or when probability drops it, and once for a ratchet. `ax_note` moves the note along the scale by AX's value, which drum patterns can't use, and `ax_velocity` adds it to the velocity, which stays from 1 to 127. Adds come before uses within a step. Going past an end stops there, or with `wrap` lands exactly on the other end, dropping what's left over. Registers are shared by every track: `SongRenderer` plays each clip once with a `RegisterRecorder` to collect changes (the same play that finds lengths, since registers only change pitches and velocities), a `RegisterTimeline` applies them in time order and then track order, and the finished clips read it with a `RegisterReader` (`src/llamatron/playback/registers.py`). Values carry from scene to scene. A scene's `reset: [AX, DX]` sets those back to their defaults as it first starts, not on its repeats, and a morph's target uses registers without adding. A note pushed outside the MIDI range goes to the nearest octave that fits.
- `direction` on a pattern sets the order its steps play in: `forward`, `reverse_a`, `reverse_b`, `alternate`, `pendulum`, `random`, `brownian` or `eitherway`, as the Cirklon names them. `direction` on a clip overrides its pattern's, but not a morph's target's. Whichever order the steps play in, a pass lasts as long as the pattern does, with the last step cut to fit, so a direction can't change how long a clip or scene is. Positions carry on across repeats, and chosen directions use the song's seed with a separate generator, so they can't change what probability rolls.
- A clip's `grab_track` names another track in the same scene, like the Cirklon's note grab, and there's no `notes_from` or `source_pattern`: the user chose grabbing from a track as simpler. Each of the pattern's `grab` steps plays the note that track most recently started, at or before the step, taking a chord's lowest note and never playing a chord of its own (a stopgap until chords can be inverted, as `LATER_IDEAS.md` says), after the other clip's chain, so a silent track gives the last note it played, and nothing played yet leaves the step's own note. The grabbing clip keeps its own rhythm, velocity and the rest, and its track's transpose, ratchet offset and note add still move the grabbed note along its scale. A morph's target doesn't grab. `SongRenderer` builds clips on demand and remembers them, so a grab just asks for the other clip, and a circle stops the render with a message naming the tracks. Lengths come from clips built without grabbing, because grabbing only changes pitches, which lets a clip grab from one that loops to fill its scene. The clip page refuses a grab that would go round in a circle, and pasting a clip drops one, using `Document.grab_circle`. Renaming a track updates grabs from it, and deleting one stops them.
- `title` and `author` are optional text at the top of a file, only for attribution when songs are shared, and blank by default. They don't affect rendering, and the Song page shows them first. `description` is optional text of any length, written as a YAML `|` block straight after them so that it reads as plain text, and kept when the tracker saves, which comments aren't. The Song page's `D` opens `DescriptionPage`, which reads first and edits after `E`, with letters as text while editing.
- Every setting in the file has a default when it's missing, including `tempo` (120), `tracks` and `scenes`, so an empty file is an empty song and a file from an older version still loads. This is a lasting rule from the user: new fields need a reasonable default too, rather than migration code, unless the format changes structurally.
- `scales` holds named scales, like `main: { root: F, type: minor }`, and new songs have `C Major`. A name can be anything, so that what `main` is can be decided later. `scale` on the song and on scenes must be one of these names. Scales resolve as scene and then song, and cells and patterns can't set one. The song can have no scale, and degrees then raise an error at build that names the problem.
- Every object is stored with its settings inline, never in a separate section, which the user made a permanent rule for every object type. So `tracks` is named tracks with their settings, like `bass: { transpose: 2, cc: [74, ~, ~, 1] }` or `kick: { drum: true }`, in order, and a track with none is `lead: {}`. A track's `mute: true` writes its clips as normal but switches the track off in the Live set, for tracks that other tracks only grab from, which the demos name with `SILENT`. Every generator setting is named, YAML stays flat with `{}` only one level deep, and cells always use the hash form inside a scene's `tracks`.
- A track's `transpose` moves every note on it along the scale at build, without changing patterns. It never applies to a drum pattern, and a track with `drum: true` never transposes at all. A track's `cc` gives the CC number for each of a pattern's four CC rows, and `~` means that lane sends nothing on that track.
- CC rows send a value from 0 to 127 at the start of a step, and a blank sends nothing, so the last value holds. Rests can hold them too, ratchets don't repeat them and probability doesn't drop them. A morph uses the target's values where the target plays, and a direction moves them with their steps. A step with `slide` ramps each of its values to that lane's next value, as on the Elektron Monomachine. Glide is still only for notes. `arps` names arpeggiators and `auto_ratchets` names AutoRatchets, each with their settings, and a chain is a list of steps like `arp: name` or `auto_ratchet: name`, with no settings of its own. A clip's `morph_style` is `left`, `right` or `middle`. A scene's `tempo_start` and `tempo_end` ramp the tempo across its `repeat`.

`GUIDE.md` is the user's guide to the text UI, which the user also edits by hand. Whenever a feature, setting, default or key in the text UI changes, update `GUIDE.md` in the same change, keeping the user's wording where it's still true. `src/llamatron/tui` is the text UI, which is meant to become the only way people use the program, and `llamatron [song]` or `./llamatron.sh [song]` opens it. It uses Textual with `ansi_color=True`, and draws with only bold, dim, reverse video and box characters, because terminal backgrounds differ. There are no tooltips, and it never saves or renders unless asked. `src/llamatron/tui/document.py` holds the song as plain file data, with everything that changes or reads it and no drawing, and it keeps references correct, so renames update everything. That's being replaced, as a firm rule from the user: the tracker must never edit the song's data directly, only through the objects' methods, so `Document` is moving onto the composition objects page by page (see `LATER_IDEAS.md`). Each screen lists its keys once in `keys()`, which both handles and draws them, so no key can work without being shown, and a test checks this. `H` shows a page's `HELP` in a dialog on every page, which has to fit an 80 by 24 console, and a test checks that too. Upper and lower case are the same key, Tab goes back and never quits, and Q quits only from the main screen. Every list a page can add to has a `+` row at the bottom, where Enter does the same as pressing `+`. On settings pages, left and right do the same as `-` and `+`. Deleting anything still used is refused with up to five uses listed, and otherwise confirms. Don't name a screen's method after one Textual has, such as `render` or `remove`, because that breaks screens in ways that only show when they close, and a test checks this too. In the pattern editor, typing never moves the cursor or grows the grid, and digits build up a number in a cell until the cursor moves or a number would be out of range. PgDn and PgUp step the rows under Degree through normal, advanced, CC, register (`+Note` and `+Vel`) and register change (`+=`) rows, because all of them can't fit an 80 by 24 console. CC rows, Slide and register changes can be set on a rest. The Registers page (`R` on the main screen) edits the registers, and the scene page has a Reset field for each. On the Tracks page, `Enter` opens a track's settings, and `N` renames. An arp's offsets have their own one-row editor. `F` reverses the steps after the cursor, `S` swaps both sides of it, and the cursor stays on its step so that pressing either again undoes it. `L` loads a copy of another pattern over this one. Pickers with many short options use `GridChoiceDialog` in `src/llamatron/tui/base.py`, laid out by `CHORD_GROUPS` in the pattern editor and `SCALE_PAGES` and `ROOT_KEYBOARD` on the Scales page. A grid can have pages, which PgUp and PgDn change, named on its top line. The scale picker shortens long names only on screen, and `+` on the Chord row follows `CHORD_GROUPS`, which a test keeps in step with `CHORD_SYMBOLS`. On a drum pattern's Note row, `A` and `F` are note letters instead. `test/test_tui_pages.py` presses real keys, and is what makes the test suite take over a minute. New pattern generators are planned for `src/llamatron/generators` and mutators for `src/llamatron/pattern_mutators`, working on patterns rather than clips.

`examples/` holds two kinds of song. `minimal_techno.yml` and `retro_chill.yml` are meant to sound good. The ones named `*_demo.yml` each teach one feature a scene at a time, described for people in `examples/DEMOS.md` and in each song's `description`, whose "When changing this demo" part says what to keep true when editing one. `test/test_demos.py` loads, renders and saves every demo without checking what it plays, so they can be edited freely. `test/demo_sources/make_demos.py` wrote the first versions of all but `registers_demo.yml`, which was written by hand (`HAND_WRITTEN` in `test/test_demos.py`), from tune data written into it, plus the Mutopia Project's public domain `entertainer.mid`, kept beside it with its LilyPond source. Run directly, it overwrites the demos, hand edits included, so it's only for starting over. The tests also run it into a temporary folder and check its output against those sources. YAML is only ever read with `yaml.safe_load`, so that loading a file can never run code. `yaml.load`, `full_load`, `unsafe_load` and custom loaders are never used, which `test/test_yaml_safety.py` checks. Tests and scripts must never fetch anything from the internet: song data a test or script needs is kept in the repository as data files, separate from the test code. Muted tracks in the demos have SILENT in their names, which a test checks.

The user wants the code easy for people to maintain without AI: plain code, comments that explain why, tests that read clearly. In the text UI tests, `select_field(label)` on `UITest` moves to a settings field by its label, using the page's own `fields()`, rather than counting key presses. `LATER_IDEAS.md` keeps feature ideas the user wants remembered for later. Add to it only when they ask.

`test/test_tracker_midi.py` checks the whole path from a song to MIDI using Mary Had a Little Lamb, and deliberately checks only that the notes and an accompaniment come out, not exact timing, so that the math stays free to improve.
