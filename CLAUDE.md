# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

llamatron is a text UI that helps people compose electronic music in MIDI, for Ableton Live and, later, other DAWs. Its features are inspired by Ableton's Session View, hardware sequencers like the Elektron Monomachine and the Sequentix Cirklon, and software trackers. `docs/WHY_LLAMATRON.md` is part of the definition of what the program is for: it says what llamatron takes from each of those, where it differs and why it composes before the DAW, and a feature is judged against it. The user edits it by hand, and it's updated when an idea it describes changes. The Python classes underneath are internal: no person is expected to use them as an API, so they can change freely to suit the tracker. It's at an early stage. The third-party dependencies are `mido`, `python-rtmidi`, `PyYAML` and `textual`, pinned in `requirements.txt`, which `setup.py` also reads. The package is `llamatron`, in `src/llamatron`, and the code and its tests import it by that name, so it has to be installed (as below) before anything runs.

## Where everything is

- `dev_notes/QUEUE.md`: the agreed work not yet built, in order, kept by Claude.

- `.claude/TESTING.md`: how the tests are run, what a change must come with, how tests are written and where each kind lives.
- `.claude/COMMUNICATION.md`: how Claude works with the user: committing, asking, numbering questions and explaining changes.
- `.claude/FORMAT.md`: the model, the file format's rules, playback, the exporters, the generators, the examples, performance and the tests of the model.
- `.claude/UX.md`: the user's rules for how the text UI behaves: keys, pickers, dialogs, the status line, wording and drawing.
- `.claude/TRACKER.md`: the text UI, page by page, with its keys and the pattern editor.
- `.claude/KEYMAP.md`: what every key does on every page, with the cursor at each kind of place, then each key's pages, then every settings page's fields, generated by `internal_tools/key_map.sh` from the key tour of `test/test_tui_help_keys.py`, whose `TestKeyMapIsCurrent` keeps it current. It isn't imported: look a key up there before reading a page's code (the user's ask), and run the script after changing a key.
- `.claude/GENRES.md`: the genre library's standing rules: what it is, what may be read, how imperfect data is weighed, and licenses. It isn't imported: read it before working on `src/llamatron/genres/`, a demo or a generator. Nothing of the genre library goes on the website until the user says so (the user's rule).

- `dev_notes/GENRE_PLAN.md`: the genre library's one plan, kept by Claude in its own words with no band, artist or composer named: what is wanted, what exists, what was measured and the steps in order.
- `.claude/DECISIONS.md`: the history of the choices behind the tracker and the format, with their dates, for when a choice is questioned. It isn't imported, so read it when a note in the other files says a thing was decided and the reason matters.
- `src/llamatron/strings/`: every piece of text the program shows or raises, one module for each
  way the text is used.
- `dev_notes/IDEAS.md`: the user's ideas for later, kept by Claude, with what each would mean for the code. The user calls it their ideas file. `dev_notes/DOCS_IDEAS.md` beside it keeps the ideas for the documentation, the guides, the website and the demo videos, apart, the user's rule, under the same rules.
- `README.md`, `GUIDE.md`, `INSTALL.md`, every chapter in `docs/` and `docs/DEMOS.md` are for people, and the user edits them by hand too. `GUIDE.md` is the documentation's home page and the website's: an introduction, the demo songs featured, and tables linking every page, which the website's sidebar is built from, each heading a group that opens and closes: Intro (`docs/WHY_LLAMATRON.md`; Installing, `docs/INSTALLING.md` with `docs/FLUIDSYNTH.md` and `docs/INSTALLING_RECORDING.md` under it; `docs/GETTING_STARTED.md`; `docs/CONCEPTS.md`), Demo Songs (`docs/DEMOS.md`, `docs/LISTENING_TO_DEMOS.md`, `docs/demos/TUTORIAL.md`, a page for each genre in `docs/demos/`, and `docs/demos/OTHER.md` last), Objects (`docs/OBJECT_MODEL.md`, `docs/PATTERNS.md`, `docs/SCENES.md`, `docs/TRACKS.md`, `docs/INSTRUMENTS.md`, `docs/ARRANGE.md`, `docs/CLIPS.md`, `docs/SCALES.md`, `docs/REGISTERS.md`, `docs/CHAINS.md`, `docs/GROOVES.md`), Generators (`docs/GENERATORS.md` and a page for each in `docs/generators/`, in six categories), File Operations (`docs/EXPORTING.md`, `docs/IMPORTING.md`), MIDI & Performance (`docs/MIDI_SETUP.md`, `docs/PLAYING_LIVE.md`, `docs/VISUALIZERS.md`) and Advanced (`docs/USER_SCRIPTS.md`, `docs/RECORDING.md`, `docs/ARCHITECTURE.md`). `INSTALL.md` points to `docs/INSTALLING.md`. Each thing is described on one page only; another links to it rather than repeating it, and titles and headings are formal, in Title Case (the user's rules).

Everything in `.claude/` is for Claude: it holds what the user doesn't need to read. `STYLE.md`, `TESTING.md`, `COMMUNICATION.md`, `UX.md` and `PRINCIPLES.md` are imported at the end of this file, so they load in every session; `FORMAT.md`, `TRACKER.md`, `KEYMAP.md` and `DECISIONS.md` are read when the work needs them. `test/test_doc_paths.py` checks that every source path these documents name exists.

## Commands

Before and after a refactoring, or any change that should leave the music alone, use `internal_tools/compare_exports.py`, which proves byte for byte that every example still exports the same (ignoring the version line in the re-saved sets), or shows which songs changed.

## Version

`src/llamatron/support/version.py` holds `VERSION`, a string of three whole numbers separated by dots, like `1.0.2`, which `setup.py` reads, the About dialog shows, and every saved set file records as `version`. Versions are compared number by number with `version_numbers()`, never as decimals. Bump the last number in every commit that changes Python code under `src/`, with `internal_tools/bump.sh` (`internal_tools/bump_version.py`) and never by hand or with a text replacement, and leave the first two to the user. `internal_tools/check_before_commit.sh` refuses when Python under `src/` is staged without a bump (`internal_tools/bump_version.py --check`), since two commits once went in without theirs when a replacement matched nothing. `BUILD_DATE` and `BUILD_TIME` beside it are the date and time of the last bump, which `internal_tools/bump.sh` writes with it, since nothing builds the program; the About dialog shows them. The example sets keep the `version` they were last saved with, and the tests that save and reload them ignore it, so a code bump never rewrites the examples: their `version` only moves when they're re-saved because the format changed. The program and the files share the one number.
