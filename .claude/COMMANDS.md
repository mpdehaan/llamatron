# Commands

Reference notes for Claude: every script of `user_scripts/` and `internal_tools/` and every tool worth running again, with what
each is for. It isn't imported: read it when a script or a tool is needed, and update it in the same change when a script is
added, renamed or changed. `CLAUDE.md` keeps only the commands every session needs.

The everyday commands are short scripts, each named after what it does with underscores and saying so in its `# What it does:` line, in two folders by who runs them (the user's layout, which replaced the Makefile), and the top folder holds only `llamatron.sh`, which starts the tracker, on a set if one is named, from the project folder without activating the environment. `user_scripts/`, plain `sh` so that `sh user_scripts/record.sh` works from the top folder, is for anyone using llamatron, and the recorders and the tools that play a set take the set's file name, the user's rule now that there are too many demos to list: `user_scripts/setup.sh`, `user_scripts/install_fluidsynth.sh`, `user_scripts/install_blackhole.sh` (BlackHole 2ch, the loopback audio device the recorder records from, with Homebrew, asking first), `user_scripts/demos_to_midi.sh` (every example as one MIDI file each in `previews/`, ignored by git), `user_scripts/demos_to_wavs.sh` (every demo as a WAV file in one go, the previews made first, through FluidSynth and the SoundFont it sets up), `user_scripts/play_demo.sh` (a demo's WAV file played with afplay, picked from a numbered list or by its number or name, its number and details said first; `--list` for the list alone), `user_scripts/launch_docs.sh` (the documentation website, as committed in `web_docs/`, served on this computer by `internal_tools/serve_docs.py` and opened in the browser, needing no Node.js), `user_scripts/demos_to_live_sets.sh` (every example as a Live set beside it), `user_scripts/demo_report.sh` (the demos as comma-separated values, a row a demo, or with `--features` a row a feature, through the `--csv` of `internal_tools/demo_summary.py` and `internal_tools/demo_features.py`), `user_scripts/record.sh` (a video of the tracker playing a set on Arrange, `--sound daw`, the default, or `--sound fluidsynth`, and with `--interactive` you start the song, perform and end the take from Arrange's corner), `user_scripts/record_all.sh` (a batch video of every example through FluidSynth, shortest first, each with its mode from `internal_tools/visualizer_pairings.yml`, through `internal_tools/record_batch.py`; `LLAMATRON_BATCH_RECORD_MAX=2` for the two shortest). `user_scripts/USER_SCRIPTS.md` says what every script there is for, with examples, and is kept current with them (the user's ask); the scripts that only write or check the documents are development tools, in `internal_tools/` (the user's rule). `internal_tools/`, which the user also calls the support folder, holds the development scripts beside the tools they run, with the genre library's tools for analysis and generation kept apart in `internal_tools/analysis_and_generation/` (the user's rule): `internal_tools/test.sh` (the whole suite), `internal_tools/test_ui.sh`, `internal_tools/test_files.sh`, `internal_tools/test_one.sh NAME`, `internal_tools/bump.sh`, `internal_tools/check_before_commit.sh` (what Claude runs before committing code), `internal_tools/demo_summary.sh`, `internal_tools/demo_features.sh`, `internal_tools/demo_table.sh` (the demo tables written into the docs), `internal_tools/sort_ideas.sh` (the ideas files kept sorted by priority, `--check` to only look), `internal_tools/layers.sh` (lists the imports that cross the program's layers the wrong way, each marked allowed or new; `--prune` takes the crossings that are gone off `tests/rules/layer_exceptions.py`, which `tests/rules/test_layers.py` holds and which only shrinks), `internal_tools/refactor_log.sh "step name"` (measures render time, import time, the suite's time, lines of code by top folder and the program's shape, and adds a row to `.claude/features/REFACTORING_LOG.md`; `--show` only prints), `internal_tools/sort_imports.sh` (lists the files whose opening imports are out of the project's order, `--write` to sort them; run after `constants_by_module.sh --write`; `tests/rules/test_import_order.py` holds the rule with it), `internal_tools/constants_by_module.sh` (lists every constant a file imports by name rather than through its module, `--write` to rewrite the files from their syntax trees, `--from PACKAGE` for only the constants a package defines; `tests/rules/test_constants_by_module.py` holds the rule with it), `internal_tools/demo_splash_screen.sh` (the start screen alone, with `--batch` a batch video's opening on the Entertainer, or with `--scroll-text WORDS` the title and then the words crossing the screen as a recording shows a demo's name, through `internal_tools/demo_splash_screen.py`), `internal_tools/pyflakes.sh`, `internal_tools/pep8.sh` (a look, not a rule), `internal_tools/loose_strings.sh`, `internal_tools/keys.sh`, `internal_tools/key_map.sh` (`.claude/KEYMAP.md`, from the key tour), `internal_tools/time.sh`, `internal_tools/time_keys.sh`, `internal_tools/time_visualizer.sh`, `internal_tools/midi_spike.sh`, `internal_tools/realtime_report.sh`, `internal_tools/iac_check.sh`, `internal_tools/capture.sh` and `internal_tools/compare.sh` (which keep their exports in `.compare_exports/`, ignored by git), `internal_tools/test_all_sample_midi_against_import.sh`, `internal_tools/diagrams.sh`, `internal_tools/screenshots.sh`, `internal_tools/make_docs.sh` (both and the demo table), `internal_tools/build_docs.sh` (the documentation website, from `GUIDE.md` and `docs/`, into `web_docs/` with VitePress, installing Node.js with a yes and VitePress into `.docs_site/`, both ignored by git but `web_docs/`, which is committed; `web_docs/` is never edited by hand), `internal_tools/publish_docs.sh` (the committed `web_docs/` pushed as the whole of the `gh-pages` branch, which GitHub Pages serves, the user's choice over GitHub Actions; it refuses while `main` holds commits GitHub's `main` doesn't), `internal_tools/push_all.sh` (the website rebuilt and committed, `main` pushed and then the website published, in that order, the one command that sends anything to GitHub, which Claude runs when asked to push), `internal_tools/preview_visualizer.sh`, `internal_tools/tutorial.sh`, `internal_tools/macro_compose.sh` (the MacroComposer, the user's name for it: a set composed from a song's input file, structured data that says what to play, with `--decompose` an existing set written as an input and with `--same-as` the two compared; with `--arrange` a whole song made from a song's picks and a style template of `src/llamatron/macro_composer/style_templates/`, a style's traits with how common each value is, the tune sketched by rule where the song gives none; a song may give each instrument's player a complexity from 1 to 4, which people see as an imaginary player's name (`src/llamatron/macro_composer/players.py`), and every track is made with a Rush and a Drag to change; its parts are in `src/llamatron/macro_composer/`, with three demos written as inputs to read in `tests/data/macro_composer_inputs/`, made by `--decompose` and made again when their demos change; it fetches nothing and looks nothing up, the user's rule, and a wizard in the tracker is to use it later) and `internal_tools/clean.sh`. Every script runs from the top folder wherever it is started and passes on what it is given, so `./llamatron.sh examples/learning/08_tie.yml` opens a set and `internal_tools/keys.sh --key s` lists every binding of S. A new everyday command gets a script of its own in the folder that fits who runs it. `docs/USER_SCRIPTS.md`, the User Scripts page under Advanced on the website, explains every script in `user_scripts/`, by category, what it does and when to use it, with an example of running it and its parameters in order, and a new or changed script updates it in the same change (the user's rule, which `tests/rules/test_doc_paths.py` holds). Set up the virtual environment once. This also installs the `llamatron` command, which `setup.py` points at `llamatron.cli:main`, and `-e` makes it use the code here rather than a copy:

```
python3 -m venv .venv
.venv/bin/python -m pip install -e .
```

`.claude/TESTING.md` says how the tests are run and written. In short: `internal_tools/test.sh` runs the whole suite in parallel, in about two and a half minutes, and `internal_tools/test_changed.sh` only the classes that cover what changed, by the map `internal_tools/test_map.sh` makes with `coverage`. There is no git hook, by the user's rule, so Claude runs `internal_tools/check_before_commit.sh` (the version check, then the tests that cover the change) before committing code, commits documents alone without a run, and `internal_tools/push_all.sh` runs the whole suite before every push.

`internal_tools/` keeps the tools worth running again, for developing llamatron. Run them from the top folder:

```
.venv/bin/python internal_tools/compare_exports.py capture /some/folder   # before a change that shouldn't alter the music
.venv/bin/python internal_tools/compare_exports.py compare /some/folder   # after it: lists every file that differs
internal_tools/analysis_and_generation/fetch_corpus.sh                                            # the genre library's corpus downloaded into .corpus/, ignored by git, development only: asks category by category with each one's size and terms, --all for everything, or the sources named
internal_tools/analysis_and_generation/corpus_tables.sh                     # every corpus source measured into tables in .corpus/tables/, rebuilt when the analyzer changes (--rebuild to force)
.venv/bin/python internal_tools/show_midi.py some.mid                     # a MIDI file's notes as names and lengths
.venv/bin/python internal_tools/loose_strings.py src                      # string literals inside functions, which should be constants
.venv/bin/python internal_tools/repeated_values.py tests                  # strings written out that repeat a value the program names, to read before committing a test (internal_tools/repeated_values.sh)
.venv/bin/python internal_tools/show_keys.py                              # every key binding of the tracker, or one page's, or every binding that has a key (internal_tools/keys.sh)
.venv/bin/python internal_tools/demo_features.py                          # which features each example uses, and which no demo shows
.venv/bin/python internal_tools/demo_summary.py                           # one line per example: its length when played, scenes, tracks and a few features, plain, bordered or Markdown (internal_tools/demo_summary.sh), and --write-docs puts the Markdown table into docs/DEMOS.md (internal_tools/demo_table.sh)
.venv/bin/python internal_tools/bump_version.py                           # raise the version's last number and set the build date and time (internal_tools/bump.sh)
.venv/bin/python internal_tools/time_renders.py                           # how long each example takes to render and how many objects a render makes (internal_tools/time.sh)
.venv/bin/python internal_tools/time_keys.py                              # how long the tracker takes to answer one key press, page by page (internal_tools/time_keys.sh)
.venv/bin/python internal_tools/time_visualizer.py                         # how long each visualizer mode takes to draw a frame, with 8 and 64 tracks, small and large (internal_tools/time_visualizer.sh)
.venv/bin/python internal_tools/midi_timing_spike.py                      # how tightly Python sends an example's MIDI in real time, from a process or a thread (internal_tools/midi_spike.sh)
.venv/bin/python internal_tools/realtime_report.py                        # the Entertainer through the Realtime Sender Process, its skew from the export, and the render time of a heavy set (internal_tools/realtime_report.sh)
.venv/bin/python internal_tools/iac_check.py                              # a scale run out of a real IAC bus and back, said note by note as it plays, the one tool that touches real MIDI (internal_tools/iac_check.sh)
.venv/bin/python internal_tools/record_demo.py SET                        # a video of the tracker playing a set on Arrange with the sound from the DAW, for the demo videos (sh user_scripts/record.sh, docs/RECORDING.md)
.venv/bin/python internal_tools/record_demo.py SET --fluidsynth           # the same video with the set's own FluidSynth instruments and no DAW (sh user_scripts/record.sh SET --sound fluidsynth)
.venv/bin/python internal_tools/record_demo.py SET --fluidsynth --batch   # a batch video: the title, READY, the mode in the frame, recorded from the window's cells alone, found by internal_tools/window_region.py
.venv/bin/python internal_tools/record_batch.py                           # a batch video of every example, shortest first, the modes from internal_tools/visualizer_pairings.yml (sh user_scripts/record_all.sh)
.venv/bin/python internal_tools/import_check.py                           # import every MIDI file in examples/midi/ and every example set into a new set: tracks, patterns, scenes, and whether it plays back the same (internal_tools/test_all_sample_midi_against_import.sh)
.venv/bin/python internal_tools/preview_midi.py                           # every example as one General MIDI file each in previews/, drums on channel 10 and each other track on its own with its sound, for a plain MIDI player (sh user_scripts/demos_to_midi.sh), made WAV files by user_scripts/demos_to_wavs.sh (sh user_scripts/demos_to_wavs.sh), which sh user_scripts/play_demo.sh plays
.venv/bin/python internal_tools/normalize_wave.py previews/classic_strum.wav       # a WAV file raised or lowered until its peak is 1 dB below full scale, which sh user_scripts/demos_to_wavs.sh runs on each
.venv/bin/python internal_tools/play_demo.py                             # the demos' WAV files numbered, and the one picked played with afplay, after sh user_scripts/demos_to_wavs.sh made them (sh user_scripts/play_demo.sh)
.venv/bin/python internal_tools/preview_visualizer.py SET                  # a set played on Arrange with the visualizer over the clips, as sh user_scripts/record.sh would record it, with no video (internal_tools/preview_visualizer.sh, docs/RECORDING.md)
.venv/bin/python internal_tools/make_video_tutorial.py SET                # the tracker builds a set from a new one, key by key as a person would, plays it, and records it into recordings/<set>_tutorial.mov (internal_tools/tutorial.sh SET)
internal_tools/macro_compose.sh INPUT --out SET                               # the MacroComposer: a set composed from a song's input file (--decompose SET --out INPUT writes a set as an input, INPUT --same-as SET compares them)
internal_tools/macro_compose.sh --arrange PICKS --out SET                     # a whole song from a song's picks and its style's template (--keep-input INPUT keeps the input made on the way)
internal_tools/loudness_steps.sh [GENRE] [--seed N]  # how big the step in loudness is into the first chorus of what the song wizard makes, a line a subgenre: as written, and as made after each player's trade; run before and after a change to a template's Energy or the trade's numbers
internal_tools/wizard_songs.sh [GENRE]  # a line for each subgenre's usual songs and for every choice once, each song a short hash (about 2,000 lines in 18 seconds, on every core): run before and after a change that should leave the wizard's songs alone, a refactoring of the arranger or of the wizard's choices, and compare the two outputs
internal_tools/monotony_report.sh [GENRE [SUBGENRE]] [--songs N] [--loudness]  # how much of what the song wizard makes repeats: the share of bars the same as an earlier bar of the section, a line a subgenre, or one subgenre's table of players by kinds of section; run before and after a change to what the wizard writes
llamatron --wizard SONG_FILE [--out SET] [--seed N] [--batch]                 # a song made from a song file as the song wizard would (.claude/features/MACRO_COMPOSER.md, "A Song File"): the set written and opened, or only written with --batch
sh user_scripts/install_fluidsynth.sh                                         # FluidSynth and its SoundFont on a Mac, from the right Homebrew, offering to install Homebrew; plain sh, for people with no make
internal_tools/rebuild_docs.sh                                       # the screenshots retaken and the website rebuilt, each committed where it changed, with no push; internal_tools/push_all.sh runs it before every push
internal_tools/build_docs.sh                                         # the documentation website into web_docs/, staged by internal_tools/stage_docs_site.py: the guide as its front page, the sidebar from the guide's tables
internal_tools/docs_modules_missing.py .docs_site                    # exit 0 when a module the website's package.json pins is missing or at another version, which is when build_docs.sh runs npm
sh user_scripts/launch_docs.sh                                            # the built website served at http://localhost:4173/llamatron/ by internal_tools/serve_docs.py, as GitHub Pages serves it, and opened in the browser
internal_tools/make_docs.sh                                               # the diagrams in docs/ARCHITECTURE.md and docs/GETTING_STARTED.md, and the screenshots
```

Before and after a refactoring, or any change that should leave the music alone, use `internal_tools/compare_exports.py`, which proves byte for byte that every example still exports the same (ignoring the version line in the re-saved sets), or shows which songs changed.
