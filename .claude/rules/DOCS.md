# The documents and the website

How `README.md`, `docs/GUIDE.md`, `docs/INSTALLING.md` and every page in `docs/` are written, edited and generated. Read before changing any of
them, the screenshots or the website.

## Who edits them

- They are the user's own writing. Claude MUST make only minimal corrections there, to remove an inaccuracy, keeping the user's
  words: no rewording, moving or tidying. A path, file name or command a change made wrong MUST always be fixed.
- Claude MAY edit them as it judges best and report what changed.
- Every reply after a change to them gives a synopsis of what changed, grouped by document.
- `CLAUDE.md`, `.claude/` and `.claude/planning/IDEAS.yml` are Claude's, to keep consistent and correct.

  Synths and Advanced, in that order. The sidebar is built from them (`GROUPED` in `internal_tools/stage_docs_site.py`), each heading a group
  that opens and closes; a `###` heading makes a group within one.

  `docs/demos/TUTORIAL.md`, a page per genre), Demos (Synth) (`docs/demos/SYNTH.md`, the demos on the built-in synths, one page

## How they are written

- Titles and headings are short, formal noun phrases in Title Case, without articles or possessives ("Screen Layout", "Melody",
  "Scene Arrangement"); a verb only where the activity is the subject ("Installing").
- A heading stands on its own in the sidebar or a search: no pronoun or reliance on the page ("Applying the Generator", not
  "Using It").
- "(Optional)" marks only an optionally installed component, on the Installing page.
- Pronouns: name the thing first; a pronoun MAY follow only where it can mean nothing else.
- Commands as a person types them: `llamatron`, `./llamatron.sh`, the scripts; never `.venv/bin/...`. Installing says
  `sh setup.sh`; only the Installing page explains the virtual environment. Setup MUST NOT need `make`.
- Music first, reference second: what a player does that the feature stands for, when a musician reaches for it, what is heard
  with and without it, in words a school band student follows, with a small example; the settings table after. The same holds
  when Claude explains a feature to the user.
- Prose flows in full sentences, without chatbot phrases ("Let's dive in."). Say a thing once and link the rest.
- The markdown wraps its prose and list items at 78 characters, so that it reads easily in a terminal (the user's ask), as
  `.claude/notes/music_theory/` does; tables, headings, code blocks, HTML comments and the parts a tool generates keep their own lines.
- The names the tracker shows, never code names that differ.

## Generated parts

- The architecture diagram between `<!-- generated by internal_tools/make_diagrams.py: crates -->` and its end marker in
  `developer_docs/ARCHITECTURE.md`: every crate of the Cargo workspace, an arrow where one uses another as its manifest says,
  and a table of each crate's folder, the first sentence of its own documentation and its modules. Run
  `internal_tools/make_diagrams.py` after adding a crate, a dependency between crates or a module; the commit check fails
  where the diagram is out of date.
- Screenshots in `docs/screenshots/`: SVGs taken by `internal_tools/screenshots.sh` from llamatron itself, with `$VERSION` in
  place of the version and the shot's name as each style's id, so a bump alone changes none.
- `.claude/reference/KEYMAP.md`, written by `internal_tools/key_map.sh` from llamatron's walk of itself.
- The map of screens in `docs/GETTING_STARTED.md` and the demo index and summaries in `docs/DEMOS.md` and `docs/demos/` stay as
  the retired Python last wrote them until their generators are back.

## Screenshots and the website

- The website and screenshots are rebuilt only before a push or when the user asks for a rebuild. A commit changing a document
  or what the tracker draws brings no rebuild and no new screenshots, and Claude MUST NOT retake a screenshot mid-work.
- A push runs `internal_tools/push_all.sh`: `internal_tools/rebuild_docs.sh` (screenshots retaken by
  `internal_tools/screenshots.sh`, only changed shots committed; the website built by `internal_tools/build_docs.sh` into
  `output/web_docs/`, which git ignores), then the push of `main`, then `internal_tools/publish_docs.sh`, which pushes the built
  site as the whole of the `gh-pages` branch that GitHub Pages serves, and refuses while `main` holds unpushed commits. A
  rebuild request runs `internal_tools/rebuild_docs.sh` alone. The built website is never committed to `main` (the user's rule).
- History is rewritten only on the user's word, with a full mirror saved to `~/Devel/backup_llamatron/` first.
