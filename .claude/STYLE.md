# How llamatron's code is written

These are the rules for anyone, or anything, that edits the code and its tests, with the reasons
behind them. They're the user's, and they're deliberate. `docs/ARCHITECTURE.md` explains the design
these rules serve, under "The rules the code keeps". `CLAUDE.md` imports this file, so it's in
force in every session. Where a test enforces a rule, it's named; a rule with no test beside it is
kept by reading.

## The rules, and why

The user wants the code easy for people to maintain without AI: plain code, comments that explain
why, tests that read clearly. Object orientation is a design goal throughout. These rules apply to
the program, the tests and `internal_tools/` alike.

**Packages say what each part is for.** `music/` values, `support/` plumbing, `composition/` the
objects a set file stores, `playback/` what plays them into a grid, `grid/` the finished clips,
`exporters/`, `importers/`, `generators/`, `tui/`, `visualizers/`, `tutorial/` the video tutorial that drives it, `genres/` the genre library (the analyzer that measures a song and the traits it fills; `.claude/GENRES.md`). New modules go in the package that says what they're for, and
a new group of them gets a package of its own. One class per file in `tui/screens/` and
`tui/dialogs/`; elsewhere a module can hold the classes that belong together, like the file-format
checks and the object they build. Files that grow past several screens are split where behaviour
groups logically, as a matter of cohesion rather than line counts. Scripts worth running again live
in `internal_tools/`, the tools for developing llamatron, or in `user_scripts/`, the scripts for anyone
using it, each with a docstring or comment saying what for and how, never in a temporary folder.

**Behaviour lives on the object that owns the data.** Everything about computing, checking or
editing a pattern is on `Pattern`, a scene keeps its own clip slots and reference updates, and so on, so
that a reader finds everything about one kind of object in one place. Prefer code that reads at the
level of the problem, with small, well-named methods and shared helpers for repeated shapes
(`llama_data.py` has `settings_by_name`, `written_settings` and `or_default` for the settings every
object holds), over low-level code that reads like "Python written in assembly".

**Objects talk through explicit methods.** A class changes another's data only through a method
like `set_name(name)`, which validates what it's given with the same check as reading a file,
the one check its setting's description holds (`composition/setting.py`), and
reads it only through one like `get_name()`, never through descriptors, properties or other
accessor magic, so that what happens is visible where it happens. A class has the getters and
setters that other code, tests included, reads and changes it through, and no more, so its
accessors show its contract. `Note`, `Chord`, `Scale`, `Rest`, `Degree`, `Held` and
`TimeSignature` are immutable. Fields on the composition objects and the grid are editable unless
the user says otherwise, through such setters. `Document` makes every change through the objects'
setters and never touches an object's data, and neither does any page; every page reads the set
through `document.setlist()` and the current song through `document.song()`.

**Every class declares `__slots__`**, so none can be added by mistake, and each class in a
hierarchy declares its own, even `()`. Dataclasses use `@dataclass(slots=True, kw_only=True)`. The
exceptions are classes that only hold constants, and subclasses of classes from outside llamatron,
like Textual's screens, enums and exceptions. `id` is read-only where a class has one.

**Arguments go by keyword.** Functions and methods take their arguments by keyword wherever a call
passes more than one, or any optional one: the parameters go after a bare `*`, so that a call names
what it passes and Python refuses a missing, extra or misspelled argument at the call rather than a
`None` check finding it later. The exceptions, listed in `test/test_keyword_only.py`, are Python's
own special methods like `__get__` and `__round__`; `Rational`, whose arithmetic is the render's
hot path and stays positional for speed, and `Length` and `Sound`, the classes of static
methods a render calls for every note; methods that Textual or `unittest` call with their own
positional arguments, like `on_key` and `compose`; forwarders that pass `*arguments, **named`
through; and functions nested inside another, which are callbacks with a local contract. The rule
cost about seven percent of render time, spread thinly over every call, and that was accepted.

**Every string used as a value or a name in code is a named constant**, never written out where
it's used, so that typos can't happen and its meaning is clear: a file key (`'root'`,
`'pattern'`), a setting, a kind (`'arp'`), a mode (`'forward'`), a note name (`NoteName.C_SHARP`
for `'C#'`, with `NOTE_NAMES`, `SHARP_NAMES`, `FLAT_NAMES` and `ROOT_NAMES` built from them), a
chord symbol (`ChordSymbol.DOMINANT7` for `'dom7'`), a key name (`tui/keys.py`), an exporter's
tag. A constant used by only one file is defined at the top of that file, and one shared between
files goes in a module of the package, like `composition/defaults.py` for defaults,
`composition/limits.py` for limits and `composition/file_format.py` for the format's names and
lists. The same goes for numbers with a meaning: `MIN_PROBABILITY` and `MAX_PROBABILITY` rather
than 0 and 100, and error messages built from those constants. Each constant is defined on its own
line, never several at once with tuple syntax like `LOW, HIGH = 0, 100`, which the user finds hard
to read. A constant nothing imports is removed. `internal_tools/loose_strings.py src` lists every string
literal left inside a function or class, and should report nothing. Literal braces in a template
are doubled, like `{{ root: F }}`.

**Data that is an array is held as an array.** A thing that is by nature a list, a bar's steps, a row of counts, is stored
as an array of real values, true and false, numbers, named constants, None for nothing, never packed into a string that code
must take apart again and a person must count the characters of: a kick's bar is sixteen booleans, never `'x...x...'`. Asking
questions of data that has to be parsed first is miserable, and a long string is no easier to edit than an array. This holds for
data files and generated modules as for objects in memory; data the program ships is a Python module of named constants that is
imported, never a text file that is parsed. A string drawn for reading, in a report or on the screen, is made from the array
where it is shown (the user's rule).

**Every piece of text the program shows or raises is a constant**, written as a template and
filled in with `.format()` where it's used, so that wording can be edited in one place and kept
consistent. This covers the text UI too: a page's labels, field names, key legends, crumbs, column
headings, prompts, dialog titles, notes, marks like `(none)`, box-drawing characters and styles
are all constants. Three prefixes say what a string is for, with no exceptions: `ERR_` for an
error message, which is anything that says what went wrong, whether raised, printed or shown in a
status line or dialog, including the dialog's title; `MSG_` for every other user-visible string
that isn't part of the data format; and `HELP_` for a page's help text. All of them live in the `strings` package, `src/llamatron/strings/`, one module for each way
text is used, so that all the wording can be read in one place: `errors.py` holds every `ERR_`
constant; `help.py` every `HELP_` constant, one multi-line string per page in which a line is a
line on the screen and a blank line is a blank line, so that help can be edited by hand without
touching code; and the `MSG_` constants are split into `labels.py` (page names, field labels,
column headings, crumbs, row labels and a picker's choices, with the classes `Crumb` and
`Column`), `legends.py` (what each key is called and does, with the class `What`), `messages.py`
(the status line's notes, dialog titles, questions and prompts), `marks.py` (what is drawn in a
cell, and the formats of numbers and header lines), `about.py` (the About dialog), `cli.py` (the
command line) and `names.py` (the names given to new things, the word for one thing of each
section, and what each kind of export is called). Within a module the constants are grouped under
a comment naming the module that uses them. `reprs.py` holds the text each class prints itself
with for a developer, as `REPR_` constants named after the class. Any readable string belongs in
this package, whatever uses it. The package's modules import only names, from
`composition/file_format.py`, `tui/keys.py` and each other, so that every other module can import
them, which `test/test_message_constants.py` checks. Strings that aren't text
for people, like key names, file modes, the format's names and the exporters' tags, keep their own
descriptive names in their own modules. Text only for people, like docstrings and comments, stays
where it is.

**A line whose purpose isn't obvious gets a name.** A regular expression or a long expression is
given a function or method whose name says what it means, such as `is_root_note(text)`. That
includes list and dictionary comprehensions: anything more than a plain copy or filter goes in a
function or method whose name says its purpose, even if it's one line.

**Messages read one way, and keys mean one thing.** How every message is worded, which keys do
what on every page, how pickers, dialogs and the status line behave and what the tracker draws
with are the user's UX rules, in `.claude/UX.md`, and a new message, key or page is checked
against them before it's added. Two rules there have a code-level side: each screen lists its
keys once in `keys()`, which both handles and draws them (a binding its class's `IN_LEGEND` leaves out is off the
legend and listed only by F1), and a settings page's action rows are
`Button`s, listed after its `Field`s and drawn by `FieldPage` below them after one blank line, so
no page draws that gap itself. Every key binding is defined in `tui/keybindings.py` and
nowhere else: one class for each page, dialog and component, named after it, each binding a tuple
of its keys, the name the legend shows and what the keys do, so that a key changes in one place
and `internal_tools/keys.sh` shows them all. Keys that step something one way or the other, like `[` and `]`,
`U` and `D` or Home and End, are a `Steps(back=, forward=)` there, and the action bound to them is
called with the direction (`STEP_BACK` or `STEP_FORWARD`), so that no handler asks which key was
pressed; only a
key that types its own character, or an arrow that moves a cursor through `cursor_moved`, is
passed its name (`wants_key=True`). Don't name a screen's method after one Textual has, such as
`render` or `remove`, because that breaks screens in ways that only show when they close.

**Tests follow every rule the program does**, and the user requires it: every rule on this page
applies to `test/` and `internal_tools/` as it does to `src/`. How the tests are run, what a change must
come with, how tests are written and where each kind lives are in `.claude/TESTING.md`.

**Performance matters.** The tracker re-renders or re-estimates the song as people edit it,
loading and saving should be quick, and real-time MIDI playback may come later. Lengths and times
are exact, never floats: `Rational`s everywhere but inside a render, where a length is a pair of
whole numbers handled by `Length` and a note is a tuple handled by `Sound`
(`.claude/FORMAT.md`, "Sounds and lengths in a render"). A pair is never compared with `<`,
`min`, `max` or `sorted`, only through `Length`, and a sound is read by its named places
(`sound[LENGTH]`), never by a bare number. The aim is fewer operations rather than a different
number type: build each note once, keep pattern steps as per-row arrays with no Step objects, work out
what can be worked out without playing, and skip whole passes that would do nothing. Any such
shortcut needs tests of both paths: the user is never okay with a condition-specific optimization
unless both paths have good tests. Speedups are proved with `internal_tools/compare_exports.py`.
An answer is worked out once and remembered until something it was worked out from changes,
never again for every row, cell or key. Everything a set file stores carries a revision
(`support/revised.py`), which every method that changes the object moves by being written under
`@notes_change`, and one `Memory` (`support/memory.py`), held by the document, keeps each answer
with the revisions of what it came from: `Document.remembered(key=, on=, compute=)`, where `on`
is the document for anything in the set, `document.outside_patterns()` for what no pattern's own
contents can change (what uses an item, which scales a pattern plays under), or the objects
themselves (a pattern and the set whose step size it takes, for the notes covering each step).
So typing into a pattern leaves what is known about everything else alone. An answer that leaves
out something it came from would go on being returned after that thing changed, so every memory
checks itself while the tests run (`Memory.check_every_answer`, in `test/ui_testing.py` and
`test/rendering.py`): a kept answer is worked out again after any change and a difference fails
the test. A key holds whatever the answer depends on that isn't in the set, like the cursor's
step or how tall a gauge is, since the check can't see those. A question asked for every cell is
asked once for the line and passed down, as the beat steps and the roll's notes are, because even
a remembered answer costs a lookup. The parsers in
`composition/checks.py` keep each written step size, time signature and number by its text, since
a text always parses to the same immutable value. A getter that parses or searches on every call is
a hotspot waiting to be found with `cProfile`, which is how each of these was. YAML is touched only
when a file is read or written (`Setlist.read_file`, `write_file`, and the checks of what a file
holds on save): in memory the set is objects, and nothing between key presses parses or dumps it,
which `test/test_yaml_safety.py` keeps by allowing only those three modules to import `yaml`.
The undo history costs a navigation key nothing: `Document.record_edit` returns at once unless a
setter ran, and an edit key pays for the data of what it changed and no more, since every stored
object keeps its own file data until it changes (`kept_data()`) and a snapshot shares the rest
with the snapshots before it. Sharing is safe only while nothing changes data once it's kept: a
caller that wants data to change asks `to_data()`, what `to_data()` returns shares no list or
dictionary with the object, and an object shares none with the data it was read from
(`test/test_kept_data.py`).

**Binding is as late as possible**, and new features keep it that way: a degree stays a degree
until the clip that plays it knows its scale, a pattern's step size and time signature are blank
until the set's apply, and a groove is chosen at render. This is about the render pipeline, which
decides what notes play and how without working out every interaction early; it never means
working something out again when nothing has changed, which "Performance matters" above forbids.
Every setting in the file has a default
when it's missing, so a file from an older version still loads and new fields need a reasonable
default rather than migration code, unless the format changes structurally. Renaming anything
never breaks anything: every reference by name is updated by the rename, and `test/test_renames.py`
checks every kind.

**Files.** Every Python file and shell script starts with the GPLv3 header, below a `#!` line and
above the module docstring, opening with `# llamatron: a music program`. Where tests go is in
`.claude/TESTING.md`.

**The guide is the way in.** `GUIDE.md` is the documentation's home page, and the website's: an
introduction, the demo songs featured, and tables that link every page in `docs/`, under the headings
Intro, Demo Songs, Objects, Generators, File Operations, MIDI & Performance and Advanced, which the website's
sidebar is built from, in that order, each a group that opens and closes (`GROUPED` in
`internal_tools/stage_docs_site.py`), a `###` heading inside one making a group within it, or the page alone when it
holds only the page of its name. Every page in `docs/` and its subfolders, such as `docs/generators/`, a page for each generator,
is linked from a row of those tables, and a new page adds its row in the same change. Titles and headings
are formal, in Title Case, never casual phrases (the user's rule). Each thing is described in one chapter only, and another chapter links to it rather than repeating it (the user's rule). Only `README.md`,
`GUIDE.md` and `INSTALL.md` are guides at the top folder (the user's rule).

**How the documents are written** (the user's rules, for `GUIDE.md`, `README.md`, `INSTALL.md` and every
page in `docs/`):

- *Titles name their subject, as briefly as possible.* A title or heading is a short noun phrase, never a
  sentence or an instruction with filler: no articles or possessives ("Screen Layout", not "The Layout of
  Every Screen"; "Check Song Settings", not "Check the Song's Settings"), and a noun where a noun names it
  ("Melody", not "Write a Melody"; "Scene Arrangement", not "Arrange a Scene"). A verb stays only where the
  activity itself is the subject, as in "Installing" or "Exporting". Titles are formal, in Title Case, and
  never casual ("Performing", not "Perform it").
- *A heading stands on its own.* Read in the sidebar, the outline or a search result, every heading says
  what its section covers, so it never leans on a pronoun or on the page around it ("Applying the
  Generator", not "Using It").
- *"(Optional)" marks only an optionally installed component, and only on the Installing page*, such as
  "Faster YAML Parser (Optional)".
- *No ambiguous pronouns.* "It", "this", "they", "its", "there" and the like give way to the thing's name
  wherever more than one thing could be meant, as in the messages to the user
  (`.claude/COMMUNICATION.md`, "How explanations and examples are written").
- *Commands as a person types them.* Usage never shows the virtual environment's paths, such as
  `.venv/bin/llamatron` or `.venv/bin/python internal_tools/...`: it shows `llamatron`, `./llamatron.sh`,
  or the scripts of `user_scripts/` and `internal_tools/`, and installing says to run
  `sh user_scripts/setup.sh` rather than spelling out what the script does. The Installing page alone
  explains the virtual environment.
- *Prose that flows.* Sentences follow from one another logically, in full sentences, never a choppy run
  of fragments, and never the stock phrases of a chatbot, such as "And that's great." or "Let's dive in."
  Say a thing once, plainly, and link the page that covers it rather than repeating it.

**Setup needs nothing first.** Instructions for people setting llamatron up, in `README.md`,
`INSTALL.md` and `GUIDE.md`, never need `make`, which a new Mac may not have yet: they give plain
commands and the scripts of `user_scripts/`, run with `sh`, like `sh user_scripts/install_fluidsynth.sh`.
Every script of the project, in `user_scripts/`, `internal_tools/` and `llamatron.sh`, is plain `sh`,
starting `#!/bin/sh`, and is named with underscores, never hyphens. A script that installs something offers to install what it needs
first, like Homebrew, and installs nothing without a yes. The scripts of `internal_tools/` are for
people developing llamatron, and the top folder holds one script, `llamatron.sh`, which starts the
tracker (the user's rules).

**Each change carries its documentation.** Whenever a feature, setting, default or key in the text
UI changes, update the page in `docs/` that describes it in the same change, using the names the UI displays, never code names
that differ. `docs/ARCHITECTURE.md` is a tour of the code for people who won't edit it, kept true the
same way. Both are the user's own writing: Claude proposes each change to their prose exactly,
as a before and an after, keeps it minimal and to what is inaccurate, and makes it once the user
confirms (`.claude/COMMUNICATION.md`, "Building and committing"). Two things in the documents come
from the code: the Mermaid diagrams between `<!-- generated by internal_tools/make_diagrams.py: ... -->`
markers in `docs/ARCHITECTURE.md` (the packages and the imports between them, described by each
package's `__init__.py` docstring) and `docs/GETTING_STARTED.md` (the map of the screens, with the key that opens
each), which `internal_tools/make_diagrams.py` rewrites in place and `test/test_diagrams.py` checks are
current, so run it after adding a package, an import between packages or a screen; and the
tracker's screenshots in `docs/screenshots/`, SVG files that `internal_tools/make_screenshots.py` takes from
the real tracker on `minimal_techno.yml`, writing `$VERSION` in place of the version and the shot's name in place of
Rich's hashed style id so that a bump alone changes none of them, and that `GUIDE.md` and `README.md` show, regenerated when a page
changes or the user asks, and only the shots whose drawing changed are committed, since each round adds to git's history for
good (the user's choice to leave the history alone and not rewrite it; when the packed repository, `git count-objects -vH`,
passes about 100 MB, Claude proposes no longer committing `web_docs/`, which repeats every screenshot). `internal_tools/make_docs.sh` runs both, and the third generated pieces are the index of the demos in `docs/DEMOS.md` and each demo's summary, its facts (the file linked to the file on GitHub, its starting key, tempo and length) and a table of only the features it uses, on its genre's page in `docs/demos/`, between `internal_tools/demo_summary.py`'s markers, which `internal_tools/demo_table.sh` rewrites and `test/test_demo_summary.py` checks; the same run keeps each genre page's sections sorted by the demo's name without its learning number, writes a linked index of them at the top of every page of demos, and writes `docs/demos/TUTORIAL.md`, the Tutorial Demos page, from the learning demos' sections in their numbered order, and `docs/demos/OTHER.md` from `examples/other/`'s by name (the user's design), so run it after adding or changing an example. GitHub draws Mermaid and shows SVG, so
the documents need no other tool. A change to the model or the tracker updates `.claude/FORMAT.md`
or `.claude/TRACKER.md`, and a change to a rule updates this file. An idea in `dev_notes/IDEAS.md` is removed
as soon as it's built, without being asked, and the finished parts are trimmed out of an idea
that's partly built; check it whenever a feature lands, since a change often finishes an idea
noted under another heading, and add to it only when the user asks. When a module moves or is
renamed, every path that names it in `CLAUDE.md`, `.claude/`, `docs/ARCHITECTURE.md`, `GUIDE.md`,
`README.md` and `dev_notes/IDEAS.md` moves with it, which `test/test_doc_paths.py` checks. The rules carry no dates; `.claude/DECISIONS.md`, the history, keeps them. A change to Python under `src/`
bumps the last number of `VERSION`; commits that only change docs, notes, tests or examples don't.

**Working with the user** is covered by `.claude/COMMUNICATION.md`: committing, asking before
building, numbering questions, and how changes are explained.

## What this project doesn't take from PEP 8

The suite runs pyflakes, which finds mistakes, and not pycodestyle, which enforces layout.
`internal_tools/pep8.sh` runs pycodestyle for a look, and `setup.cfg` lists what it leaves out: long lines
(E501), because a line runs as long as it needs to read as one thought and about a thousand are
over 120 characters without one being wrong; the blank-line counts around definitions (E302,
E305); and a blank line at the end of a file (W391). What's left is worth a look, and `dev_notes/IDEAS.md`
notes the ones under consideration, but nothing pycodestyle reports is a rule unless it's on this
page.
